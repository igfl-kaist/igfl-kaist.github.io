# IGFL 이메일 인증과 Apps Script 설계

2026년 10월 16일 사용자 지시에 따라 가입·로그인을 모두 **KAIST 이메일 숫자 6자리 인증번호** 방식으로 한다. 유효시간은 **5분**이며 비밀번호 설정·비밀번호 로그인·비밀번호 찾기는 제거한다. 인증 백엔드는 **Google Apps Script와 비공개 Google Sheets를 우선 사용**해 비용을 최소화한다. 실제 구현을 시작했으며 현재 검증 상태와 배포 절차는 [인증 배포 안내](AUTH_DEPLOYMENT.md)에 기록한다. 이 문서의 설명은 설계 기준이며 실서비스 연동 완료를 뜻하지 않는다.

## 화면과 사용자 흐름

1. GitHub Pages의 로그인 또는 선수 등록에서 KAIST 이메일을 입력한다.
2. 인증 요청을 누르면 서버가 정확한 허용 도메인·발송 제한을 검사한다. 기본 허용은 `kaist.ac.kr`이며 하위 도메인은 자동 허용하지 않는다.
3. 서버가 숫자 6자리 코드를 발급하고 발급·만료와 검증 정보를 비공개 저장소에 기록한다. 메일 발송은 Apps Script 소유 계정의 GmailApp 또는 최소 권한으로 필요한 기능을 충족하는 메일 서비스를 사용한다.
4. 사용자는 화면에 표시되는 남은 시간 안에 코드를 입력한다. 만료·오입력·재발급 상태를 안내한다.
5. 검증 성공 시 코드를 소비하고 서버에서 확인 가능한 로그인 세션을 발급한다. 기존 선수는 내 선수 활동으로 이동한다.
6. 미등록 사용자는 인증된 이메일로 프로필·필수 동의를 작성해 바로 등록한다. 별도 운영진 가입 승인은 없다.
7. 유효한 세션을 유지하는 동안 페이지를 옮길 때마다 메일을 다시 보내지 않는다. 로그아웃·세션 만료 후에는 새 코드로 로그인한다.

가입과 로그인은 같은 인증 모듈을 사용하되 요청 목적·challenge·이메일을 연결한다. 코드나 세션을 검토 시안의 대화 상태에 저장하지 않는다. 운영 화면에서는 시안 체험용 코드를 노출하지 않는다.

## 사용자가 제시한 초안에서 보완할 점

### JSON 응답과 CORS

`ContentService.createTextOutput(...).setMimeType(JSON)`은 응답 형식을 정한다. 이것만으로 GitHub Pages 브라우저의 CORS 성공이 보장되지는 않는다. ContentService는 응답을 `script.googleusercontent.com`의 일회성 URL로 리디렉션한다. 구현 시 JSON 형식, 리디렉션, 브라우저의 CORS·사전 요청을 각각 검증한다. [Google ContentService](https://developers.google.com/apps-script/guides/content), [브라우저 CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

우선 후보는 HTTPS `POST`와 `URLSearchParams` 등으로 단순 요청을 만드는 것이다. 이는 불필요한 사전 요청을 줄일 수 있을 뿐 응답 읽기까지 보장하지 않는다. 실제 배포 URL과 실제 Pages 출처에서 로그인하지 않은 브라우저·모바일로 성공·실패 응답을 읽는 검증을 먼저 한다. `curl`에서 성공한 것만으로 브라우저 연동을 완료했다고 하지 않는다.

`mode: no-cors`의 읽을 수 없는 응답, JSONP, 이메일·OTP·세션을 GET 쿼리에 넣는 방식으로 인증을 우회하지 않는다. 직접 fetch가 동작하지 않으면 Apps Script HTML Service의 인증 화면과 `google.script.run` 통신을 대안으로 검토한다. 이 API는 Apps Script가 제공하는 페이지에서 사용한다. Pages에 임의로 코드를 붙이면 동일하게 동작한다고 가정하지 않는다. 필요하면 인증·보호 화면을 Apps Script 호스트로 옮기는 안과 별도 게이트웨이 안을 비교해 사용자에게 제시한다. [서버 함수 통신](https://developers.google.com/apps-script/guides/html/communication).

이 연동 검증은 실제 구현 첫 단계의 기술 점검이다. 실제 Apps Script 배포와 로컬 브라우저의 직접 fetch·메일 인증·세션 유지를 확인했다. GitHub Pages 출처의 직접 fetch는 지원 플랜 준비 후 별도로 검증한다. 상세한 실제 결과와 자동 테스트의 범위는 [배포·검증 기록](AUTH_DEPLOYMENT.md)을 따른다.

[GitHub Pages 제한](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)은 민감한 거래에 Pages를 쓰지 않도록 안내한다. OTP로 바꿨다는 이유만으로 호스팅 정책 검토가 불필요해지는 것은 아니다. 실제 인증 입력을 Apps Script HTML Service에 두고 Pages는 공개 화면·로그인 진입을 담당하게 하는 안도 함께 검토한다.

### 성공 여부와 로그인 세션

`{ success: true }`를 받아 화면만 전환하거나 로컬 저장소에 로그인 여부를 쓰는 것은 실제 인증이 아니다. 검증 성공 후에는 위조하기 어려운 세션을 발급하고 서버가 사용자·만료·폐기 상태를 확인해야 한다. 팀 관리, 탈퇴, 대표 교체, 경기 등록·승인 등 모든 보호 작업에서 세션과 현재 역할·소속을 다시 검사한다.

세션 토큰은 충분한 엔트로피를 갖추고 서버에는 검증값과 사용자·만료·폐기 시각을 저장한다. 클라이언트 저장 방식·세션 유지 기간은 실제 호스트의 쿠키·스토리지 동작을 확인한 뒤 정한다. Apps Script에서 HttpOnly 쿠키나 안전한 세션 기능이 자동 제공된다고 가정하지 않는다. 브라우저가 보낸 역할·학번·팀 ID를 본인 확인으로 신뢰하지 않는다.

리그 API가 별도 백엔드에 있다면 Apps Script의 인증 결과를 서버끼리 검증할 연결이 필요하다. Apps Script의 성공 응답이 다른 인증 서비스 세션으로 자동 바뀌지 않는다. 인증용 Sheets를 선택한 것이 전체 경기·Elo 저장소도 Sheets로 확정했다는 뜻은 아니다.

## 코드와 저장소

사용자가 제시한 이메일·코드·생성 시간 3개 열에 다음 상태를 보강한다.

| 데이터 | 필요한 값 |
| --- | --- |
| 인증 요청 | challenge ID, 정규화 이메일, 목적, 발급·만료 시각, 실패 횟수, 소비·폐기 시각 |
| 코드 검증 | 서버 비밀값으로 보호한 HMAC 등 검증값. 6자리 원문·단순 성공 표시를 공개하지 않음 |
| 발송 상태 | 요청 ID, 발송 대기·성공·실패, 재시도와 발송 제한 집계 |
| 세션 | 검증값, 사용자 ID, 발급·만료·폐기 상태 |

시트는 비공개로 유지하고 프런트엔드에 Sheets 읽기 권한이나 전체 시트 데이터를 제공하지 않는다. 코드 원문·토큰을 URL·실행 로그·오류 응답에 남기지 않는다. 서버 비밀값은 비공개 Script Properties 등 서버 영역에 두고 공개 저장소나 브라우저로 내보내지 않는다.

숫자 코드는 예측 불가능한 서버 발급을 사용한다. 단순 `Math.random()`을 안전한 인증 난수라고 간주하지 않는다. Apps Script의 난수 기능만으로 요구를 충족하는지 확인하고, 필요하면 안전하게 만든 서버 비밀키와 고유 요청값을 사용하는 검증된 HMAC 기반 발급을 설계한다. 엔트로피와 키 생성·보관 방법을 구현 인계에 기록한다.

코드 검증·소비·실패 횟수 갱신과 재발급 무효화는 동시 요청에도 한 번만 적용한다. Sheets를 쓸 때 [LockService](https://developers.google.com/apps-script/reference/lock/lock-service)로 임계 구역을 보호하고 발송 중 장시간 잠금을 유지하지 않도록 요청 상태를 설계한다. 잠금이 DB 트랜잭션처럼 모든 쓰기를 자동 롤백한다고 가정하지 않는다.

## 배포 권한과 메일 한도

로그인 전 이용자가 호출할 웹 앱은 소유자 권한 실행·익명 접근 허용을 후보로 하되 실제 계정과 학교 Workspace 정책에서 지원되는지 확인한다. ‘Anyone’은 호출 허용이며 선수·운영진 권한 부여가 아니다. 공개 요청은 발송·검증에 필요한 최소 동작만 허용하고 모든 보호 작업은 세션 검사를 거친다. 소유자의 Google OAuth 토큰을 클라이언트로 보내지 않는다. [웹 앱 권한](https://developers.google.com/apps-script/guides/web).

Google 공식 할당량 문서의 메일 수신자 한도는 일반 계정 **100명/일**, Workspace **1,500명/일**이다. 계정·시험판·정책과 다른 메일 제한이 추가로 적용될 수 있고 한도는 변경될 수 있다. 가입·로그인 OTP, 내부 심판 요청과 운영진 메일이 같은 발신 계정을 쓰면 함께 예산을 사용한다. [공식 할당량](https://developers.google.com/apps-script/guides/services/quotas).

2026-10-16 14:30 KST 지정 소유 계정에서 `inspectRuntimeStatus()`로 실제 `MailApp.getRemainingDailyQuota()`를 조회한 결과 **1,499 수신자분**이 남아 있었다. 이는 조회 시점의 잔여량이며 1,499통이 매일 보장된다는 뜻이 아니다. Google 한도는 사용자별이고 첫 요청 후 24시간을 기준으로 초기화된다. [MailApp 조회 의미](https://developers.google.com/apps-script/reference/mail/mail-app#getRemainingDailyQuota()). IGFL의 전체 24시간 인증 발송 예약 50회 제한은 유지했다. 선수 100명 모집 전에는 예를 들어 300회로 높이고 심판·운영 알림용 여유를 남기는 방안을 검토한다.

정확한 `@kaist.ac.kr` 인증은 사용자 승인으로 허용했다. 웹 가입 주소와 Google 발신 소유 계정 주소는 일치할 필요가 없다. 지정한 연구실 Google 계정에서 현재 프로젝트 소유자 실행·공개 웹 앱 배포·할당량 조회가 성공했다. 학교 계정의 리그 개인정보 저장 허용 정책·계정 만료·인계와 데이터 처리 조건까지 확인했다는 뜻은 아니다.

이메일별 재발송 간격·검증 시도 횟수·일일 예산·전체 발송 차단을 서버에서 설정한다. 잔여 수신자 할당량과 실패를 확인하고 한도 초과 시 무한 재시도하지 않는다. 클라이언트가 보내는 IP나 성공 플래그를 제한 검증에 신뢰하지 않는다. 소규모에서 무료 한도로 운영하는 방향이지만 무제한 발송이나 항상 0원인 전체 서비스를 보장하지 않는다.

## 구현 검증

- 실제 Pages 출처에서 Apps Script 응답을 읽고 리디렉션·CORS·모바일·비로그인 상태를 검증한다.
- 정확한 `kaist.ac.kr`만 허용하고 `kaist.ac.kr.evil.example`이나 임의 하위 도메인을 거절한다.
- 만료·재발급·이메일 변경·동시 검증·과도한 오입력과 중복 발송을 검증한다.
- 성공한 코드는 재사용할 수 없고 위조 세션·만료·로그아웃 세션으로 보호 작업을 수행할 수 없어야 한다.
- Anyone 호출만으로 시트 열람·역할 변경·경기 승인·메일 남용이 가능하지 않은지 확인한다.
- 무료 메일 예산 초과·일시 발송 실패에서 안내와 재시도가 정상 동작하는지 확인한다.

현재 작업 범위에서는 위 설계와 시안을 보완한다. 사용자가 실제 구현·설정을 지시하기 전 Google 계정 접근·시트 생성·Apps Script 배포·실제 이메일 발송을 시작하지 않는다.
