# IGFL 미정 사항과 구현 제안

기준일: 2026년 10월 16일. [기획안](PRODUCT_SPEC.md)의 확정 요구와 구분하여 읽는다. 각 항목의 확정·기본안·미정 상태를 구분한다. 최신 사용자 지시로 개인 계정 저장소, 탈퇴·재영입, 대표 교체 승인과 인원 미달 유예가 정해졌다. Elo·개인 기록 기본값은 위임에 따라 채택했다.

## 결정 순서

[최종 구현 지침](IMPLEMENTATION_BRIEF.md)의 확정 기능은 유지한다. 아래 사항을 전부 결정해야 화면 개발을 시작할 수 있는 것은 아니다. 필요한 기능을 연결하기 전에 관련 항목만 확인하며 나머지 작업은 진행한다. 답변은 해당 항목에 기록하고 관련 기획·검증 기준도 갱신한다.

| D06 | 시즌·대회 점수 정책만 미정 | 현 시즌은 초기 1000·K32·척도400·최종 승리1/패배0, 경기 일시·ID 순서와 공동순위로 채택. 시즌 이월·컵 Elo는 미정. RATING_POLICY.md 참조 |

최근 5경기·심판 공로 시즌 상위 3위는 이제 채택한 기본 규칙이다. 외부 심판 수락 체크는 D11의 기본안이며 필요하면 세칙을 보완한다. 사용자는 현 경기 운영 범위로 우선 진행하기로 했다. 예외 세칙 때문에 정상 경기 구현 전체를 다시 질문하며 멈추지 않는다. 불일치가 없거나 미응답 시간이 지났다는 이유만으로 양 팀 확인·최종 승인을 생략하지 않는다.

### 대회 운영 전에 정할 사항

상위 8개 팀 토너먼트와 컵의 관계, 정확한 일정, 최소 경기 수, 같은 상대 반복 경기 제한 여부, 랭킹 마감·동률·8팀 미만 처리, 시드, 컵 Elo와 휴지기 규칙은 대회 운영 전에 확정한다. 시즌 이월은 D06과 함께 정한다. 자율 경기 핵심 기능과 독립적으로 준비할 수 있다.

### 구현 agent가 제안할 기술 세부값

| 항목 | 아직 확정하지 않은 값과 처리 |
| --- | --- |
| 인증 제한 | 재발송 간격·오입력·일일 발송량. 시안의 5회는 예시이며 서버 검증·남용 방지 설정안을 제시 |
| 팀 이미지 | 허용 형식·용량·비율·크롭·저장 시점. JPG·PNG·WebP / 3MB는 시안 제안 |
| 접근성과 모바일 | 디자인 톤을 유지하며 대비·입력 글자·클릭 영역·키보드 동작 조정 |
| 화면 갱신과 무작위 목록 | 공개 구독·재연결, 방문 단위 순서와 페이지네이션 중복 방지 방식 |
| 메일과 장애 대응 | 중복 발송 방지, 재시도·기록·모니터링, 데이터 백업과 복구 절차 |

이 항목은 반드시 사용자가 모든 숫자를 직접 정해야 한다는 뜻이 아니다. agent가 선택 이유와 검토 가능한 설정안을 제시하고, 사용자 운영 정책·비용·데이터 공개 범위를 바꾸는 선택은 확인한다. 필요한 결정만 묶어 질문하며 미정인 운영 정책을 기술 기본값으로 조용히 확정하지 않는다.

## 채택한 Elo와 개인 기록

[계산·집계 규칙](RATING_POLICY.md)에 초기 1000점·K=32·척도 400, 최종 승리 1·패배 0, 승부차기 동일 처리와 경기 일시·ID 순서 계산을 정의했다. 같은 점수 팀 경기의 변화는 +16·-16이다. 점수 차는 반영하지 않는다. 정밀한 점수를 보관하고 정수로 표시하며 정확한 동률은 공동순위다.

개인 득점은 현 시즌 각 선수의 최근 출전 5경기, 심판 공로는 현 시즌 공식 내부 심판 경기 수를 기준으로 상위 3위를 표시한다. 5경기 미만은 실제 출전 수, 동률은 공동순위와 경계 동률 전원 표시, 0기록은 제외한다. 외부 심판은 공로 기본 보드에서 제외한다. 팀 이동으로 선수의 현 시즌 기록을 초기화하지 않는다.

시즌 이월·컵 Elo·진출 동률·최소 경기 수와 반복 상대 제한은 시즌 세칙에 남긴다. 동률 내 화면의 이름·ID 순서는 진출 우선권이 아니다.

## 시즌과 예외 규칙

- 10월 말~11월 중 정확한 시즌 마감일과 토너먼트 날짜.
- 상위 8개 팀 토너먼트와 컵 대회가 동일한 대회인지 별도인지.
- 상위 8개 팀 선정 기준: 랭킹 마감 시점, 최소 경기 수, 동률, 참가 가능한 팀이 8개 미만인 경우.
- 토너먼트 대진·시드, 컵 경기 Elo 반영 여부.
- 약 3개월 휴지기의 정확한 범위, 휴지기 경기 인정, 다음 시즌 시작일과 Elo 초기화·이월.
- 결과 확인 기한, 미응답 알림과 운영진 개입 기준. 무응답을 자동 승인으로 취급하지 않는다.
- 자책골, 승부차기 세부 방식, 취소·중단·몰수 경기 처리. 중단·몰수를 보통 경기의 정상 승패로 임의 변환하지 않는다.
- 확정 결과 이의 기한, 정정 요청자와 최종 처리 권한, 정정 후 재확인 범위.

대회 세칙이 미정인 동안 기본 자율 경기·Elo 기능과 독립적으로 설계한다. 컵 대진표 자동 생성과 휴지기 자동 전환은 세칙 확정 뒤에 구현한다.

## 기술 구성 제안

| 구성 | 제안 | 목적 |
| --- | --- | --- |
| 소스 소유 | 사용자 기존 개인 계정의 별도 저장소 | 확정 방향. 기존 개인 홈페이지 보존 |
| 프런트엔드 | React, TypeScript, Vite | 정적 빌드와 모바일 웹 UI |
| 웹 호스팅 | GitHub Pages | 학교 도메인 없이 정적 파일 제공 |
| 인증 | Apps Script·비공개 Google Sheets 우선 | 가입·로그인 6자리·5분, 발송·코드 검증과 서버 세션. 실제 CORS·권한·한도 검증 필요 |
| 리그 저장소 | 별도 DB 또는 Sheets 기반 검토 | 인증 선택과 별개. 원자적 처리·재계산·접근 제어 충족 필요 |
| 권한 | 데이터베이스 RLS와 필요한 서버 함수 | 본인·팀 대표·심판·운영진 권한 강제 |
| 확정 처리 | 트랜잭션을 사용하는 서버 함수 또는 DB 함수 | 승인 상태 변경과 Elo 적용의 원자성 |
| 화면 갱신 | 공개 데이터용 Realtime 구독 등 | 경기 확정 후 파워랭킹 갱신 |
| 메일 발송 | 서버의 메일 제공자 연결 | 가입·로그인 학교 이메일 6자리 인증·운영진 알림·심판 후보 요청 |
| 프런트 배포 | GitHub Actions | 정적 빌드·검증·Pages 배포 |

개인 계정 저장소·이메일 OTP·Apps Script 우선 방향은 사용자 선택이다. 나머지 기술 제공자와 리그 저장소는 후보이며 사용자가 최종 선택하기 전 서비스 계정이나 유료 플랜을 만들지 않는다. 라이브러리·서비스의 구체적인 버전과 요금·제한은 구현 시 공식 문서에서 다시 확인한다. 회원은 GitHub 계정이 필요하지 않으며 GitHub 계정은 개발·운영 담당자의 코드 관리용이다.

GitHub Pages에는 서버 프로세스나 데이터베이스를 배포하지 않는다. 웹 URL과 백엔드 URL을 분리하고, 정적 프로젝트의 하위 경로·직접 URL 진입·인증 후 복귀를 검증한다. 프런트엔드 공개 설정과 서버 전용 비밀키를 구분한다. Pages 소스에 실제 선수 데이터나 인증 비밀을 저장하지 않는다.

Supabase를 선택하면 노출 테이블의 권한과 RLS를 함께 설정하고, 공개 뷰·서버 함수·실시간 구독을 통한 정보 유출도 검사한다. 서비스 역할 키는 서버에만 둔다. Realtime은 갱신 전달을 담당하며 랭킹의 공식 상태는 DB의 확정 기록이다. 연결이 끊겼다가 복구되면 공식 상태를 다시 읽는다.

| 시즌과 대회 | 운영 기간, 규칙 버전, 경기 연결 |
| 경기와 심판 배정 | 시간·장소·두 팀·요청 버전, 내부/외부 심판, 후보별 요청·거절·종료, 유일한 담당 심판과 수락·적격성 이력 |
| 경기 출전 명단 | 사전/실제 구분, 당시 팀 소속 스냅샷 또는 이력 참조 |
| 결과 버전과 득점 | 정규시간·승부차기 분리, 승자, 버전별 득점 기록 |
| 팀 확인과 최종 승인 | 결과 버전, 팀, 확인자, 역할, 시각 |
| Elo 기록 | 경기 전후 점수, 변화량, 순서, 규칙 버전 |
| 이의와 운영진 처리 | 이견, 자격 확인, 정정 사유, 처리 이력 |
| 홈페이지 알림과 메일 발송 기록 | 승인 대기, 운영진 메일의 재시도·중복 방지 |

생년월일 같은 비공개 값은 공개 스냅샷에 복사하지 않는다. 역할·최종 승인·소속 정원·단일 소속·Elo 중복 반영을 브라우저 요청만 믿고 갱신하지 않는다. 병행 요청에도 데이터베이스 제약과 트랜잭션으로 일관성을 유지한다.

## 저장소와 호스팅

사용자는 기존 개인 계정에 별도 비공개 `igfl` 저장소를 만들어 개발하기로 했고 실제 생성했다. 새 Organization이나 별도 공유 계정을 만들지 않는다. 현재 플랜의 비공개 Pages 제한을 확인했으므로 호스팅 방향을 추가로 정한다. 기존 개인 홈페이지 저장소·주소는 보존한다.

공개 저장소의 Pages는 GitHub Free에서 사용할 수 있고 프로젝트 주소는 `<사용자>.github.io/<저장소>/`다. 비공개 저장소 Pages는 지원 유료 플랜이 필요하다. DB·메일·인증·이미지 저장·독립 도메인 비용은 별도이며 서비스 전체가 무조건 무료라고 보장하지 않는다. [공식 Pages 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)를 2026년 10월 16일 확인했다.

이메일 코드는 비밀번호 없이 Pages 입력과 Apps Script 검증을 우선 검토한다. JSON 형식만으로 CORS가 해결되는 것은 아니므로 실제 브라우저 연동을 먼저 검증한다. 대안은 Apps Script HTML Service 인증 화면이며 세션과 보호 API는 AUTH_APPS_SCRIPT.md를 따른다. 비밀번호 기본안은 최신 사용자 지시로 폐기했다.

운영 인계는 저장소 협업자 권한과 백엔드·메일 소유권을 문서화한다. GitHub 권한과 홈페이지 운영진·팀 대표 권한을 혼동하지 않는다.

## 구현 순서

1. 사용자에게 구현 지시를 받은 뒤 저장소 상태와 미정 사항을 확인하고 기술 구성을 확정한다.
2. GitHub 소유자·저장소 공개 범위·서비스 계정을 준비한다. 기존 로컬 Git 저장소를 유지한다.
3. 인증·개인정보 분리·역할 모델·DB 제약을 먼저 구현한다.
4. 선수 자동 등록, 팀 승인, 영입·방출·본인 즉시 탈퇴·대표 교체 승인·유예와 정원 검증을 구현한다.
5. 경기 사전 등록과 심판 배정·수락, 명단 복수 선택을 구현한다.
6. 결과 버전, 양 팀 확인, 심판/운영진 최종 승인, 이의 처리를 구현한다.
7. 합의된 Elo 설정으로 원자적 확정과 순위 갱신을 구현한다.
8. 학교 이메일 인증·심판 후보 요청·운영진 메일과 홈페이지 알림을 연결한다. 실제 수신자를 대상으로 하는 테스트 발송은 사용자와 조율한다.
9. 권한·동시 요청·기록 정정·모바일 흐름을 검증하고 Pages 배포 및 운영 인계를 진행한다.
10. 대회 규칙이 확정되면 상위 8개 팀 토너먼트·컵·휴지기 운영을 확장한다.
